## File-by-file Kotlin → Swift mapping

### Directly portable (algorithm/protocol, no Android API dependency)

| Android (Kotlin) | Swift | Notes |
|---|---|---|
| `PxcFrame.kt` | `Sources/Protocol/PxcFrame.swift` | Cmd constants + 16-byte framing. Port the full cmd-ID table verbatim (comments included — they're the verification history). |
| `PxcHandshake.kt` | `Sources/Protocol/PxcHandshake.swift` | State machine dispatcher. `handle(tag:frame:connection:)` mirrors the Kotlin `when(frame.cmd)` switch. |
| `BikeProfile.kt` + `BikeProfiles` object | `Sources/Protocol/BikeProfile.swift` | Protocol → Swift `protocol BikeProfile` + concrete conformances (`Cfdl16Profile` primary for Aura 150). |
| `QrData.kt` | `Sources/Protocol/QrData.swift` | URL query parsing — trivial port. |
| `RsaKeys.kt` | `Sources/Protocol/RsaKeys.swift` | Swap `java.security.KeyPairGenerator` for `SecKeyCreateRandomKey` + Keychain storage. |
| `AdaptivePolicy` (in `AdaptiveVideoController.kt`) | `Sources/Services/AdaptiveVideoController.swift` | Pure math (AIMD bitrate stepping) — port the thresholds/constants unchanged, replace `PowerManager.getThermalHeadroom()`/thermal-status listener with `ProcessInfo.processInfo.thermalState` + `NSNotification.Name.NSProcessInfoThermalStateDidChange`. |
| `HuTimeSync` / `HuQueryTime` | `Sources/Protocol/ClockSync.swift` | Wall-clock ack formatting — pure string/byte formatting, port as-is. |

### Needs an iOS-native rewrite (same *purpose*, different platform API)

| Android (Kotlin) | Swift | What changes |
|---|---|---|
| `EasyConnProber.kt` | `Sources/Networking/EasyConnProber.swift` | `ServerSocket`/`Socket` (java.net) → `NWListener`/`NWConnection` (Network.framework). Keep the exact port numbers, probe sequence, and reconnect/backoff constants from the Kotlin source — only the socket API changes, not the behavior. |
| `BikeWifi.kt` | `Sources/Networking/BikeWifiManager.swift` | Android's `WifiNetworkSpecifier` has no iOS equivalent (apps can't silently join arbitrary Wi-Fi). Implement as: (1) iOS 16+ `NEHotspotConfiguration` API — CAN join a Wi-Fi network programmatically given SSID+password, no MDM needed, just prompts the user once. Use this as the primary path. (2) Detect current SSID via `NEHotspotNetwork.fetchCurrent(completionHandler:)` (iOS 14+, no extra entitlement needed for reading, but confirm during implementation) for confirming we're actually on the bike's network before starting the TCP listeners. |
| `VideoPipeline.kt` (encoder half) | `Sources/Video/H264Encoder.swift` | `MediaCodec` → `VTCompressionSession`. Same profile/bitrate/keyframe targets (see protocol doc §5). |
| `AaCompositor.kt` (letterbox math only — ignore the AA-decoder-input half) | `Sources/Video/NavigationCompositor.swift` | The *letterbox/aspect-fit math* (`mapCanvasToSource`, margin calculation) ports directly — it's pure geometry. The *source* is different: instead of compositing an Android Auto decoder's output texture, render an off-screen `MKMapView` (or a `SwiftUI` map view via `ImageRenderer`/`UIGraphicsImageRenderer`) into a `CVPixelBuffer` on a timer matched to the target fps. |
| `TripRecorder.kt` | `Sources/Services/TripRecorder.swift` | `LocationManager`/`FusedLocationProvider` → `CLLocationManager` + delegate. |
| `MediaButtonBridge.kt` | `Sources/Services/MediaButtonBridge.swift` | `ACTION_MEDIA_BUTTON` broadcast receiver → `MPRemoteCommandCenter` targets. Port the double-tap/long-press timing state machine logic as-is (it's pure timer logic), just swap the event source. |
| `AppSettings.kt` / `BikeMemory.kt` | `Sources/Models/AppSettings.swift` / `BikeMemory.swift` | `SharedPreferences` → `Codable` structs persisted via `UserDefaults` (or a small JSON file in `Application Support` for anything array/dictionary-shaped that SharedPreferences handled awkwardly anyway). |
| `LogBus.kt` | `Sources/Services/LogBus.swift` | Android `Log` + in-memory ring buffer + Share-file → `os_log` + the same in-memory ring buffer pattern + `ShareLink`/`UIActivityViewController` for export. Keep the same `[TAG]` prefix convention. |
| `AndroidAutoService.kt` (orchestration half only — NOT the AA receiver half) | `Sources/Services/ConnectionSupervisor.swift` | Foreground `Service` + wake locks → iOS background task model: `BGProcessingTask`/`BGContinuedProcessingTask` where possible, plus the fact that iOS will NOT keep raw TCP servers alive indefinitely in the background — **this is a real platform constraint, not a porting detail; see the "Background execution reality" section below.** Port the watchdog timer / reconnect-backoff / grace-window logic as pure state-machine code, independent of how backgrounding is eventually solved. |

### NOT ported — Android Auto specific, no iOS equivalent, out of scope

Everything under `reference/android-source/java/dev/zanderp/opencfmoto/aa/` (`AaReceiver`, `AapTransport`,
`AapControl`, `VideoDecoder`, `AapMessage*`, `ServiceDiscoveryResponse`, etc.). This package exists only
to *receive* Android Auto's own video stream. AuraLink has no such upstream source — it generates its own
navigation frames directly from MapKit. Read this package only for the *downstream* shape it hands off to
`VideoPipeline` (a `Surface`/frame source feeding an encoder) — that handoff shape is what
`NavigationCompositor` reproduces, just with MapKit as the producer instead of an AA decoder.

### UI — full rewrite, SwiftUI-native (no line-by-line mapping — same screens, iOS-idiomatic layout)

`MainActivity`, `SetupActivity`, `ControlsActivity`, `GarageActivity`, `TripActivity`/`TripMapActivity`,
`TripsListActivity`, `ButtonMappingActivity`, `ScreenMarginsActivity`, `AboutActivity` → one SwiftUI
`View` each in `Sources/UI/Views/`, composed under a `TabView` or `NavigationStack` root. Match the
Android app's information architecture (home → Connect/Dash/Controls/Setup/Garage/Trips/Settings) since
that's a validated, bike-tested UX, but use standard iOS navigation idioms (NavigationStack, not a
custom back-stack).

## Background execution reality (read this before designing `ConnectionSupervisor`)

This is the biggest platform-level risk in the whole port, bigger than any protocol detail, and it did
not exist on Android (where a foreground `Service` + wake lock keeps sockets alive indefinitely). **iOS
suspends apps in the background within seconds unless a background mode keeps them alive**, and raw TCP
listen sockets are not one of the things standard background modes keep running indefinitely.

Practical implication for a rider who locks their phone mid-ride (which the Android app explicitly tells
users to do):

- `UIBackgroundModes: location` keeps the app alive as long as it's actively using significant-location-
  change or continuous location updates — **this is the most realistic way to keep the process (and thus
  the TCP servers) alive for the duration of a ride**, piggybacking on the fact that AuraLink is already
  doing GPS trip-logging. This is a legitimate, App-Store-safe use of the location background mode
  (it's not being requested solely to keep sockets open — the app genuinely needs continuous location
  for trip recording — but Apple's review is unpredictable, and Miel should be told there is real risk
  the app could get rejected specifically for holding a socket server open under a location background
  mode whose primary use looks like something else. Flag this explicitly in the app's review notes.)
- `UIBackgroundModes: audio` similarly keeps a process alive if it's playing/routing audio — not
  applicable unless AuraLink is also handling turn-by-turn voice prompts, which it should (`GpxVoice.kt`
  equivalent), giving a second legitimate anchor for staying alive.
- Practically: **build and test this exact scenario first**, before investing in UI polish — connect,
  lock the phone, confirm the dash keeps receiving frames for a multi-minute stretch. If iOS still
  suspends the app, the fallback is to tell riders to keep the phone screen on/unlocked (worse UX, but
  it is a truthful, functional fallback — document it plainly for Miel rather than silently shipping
  something that stops working the moment the screen locks).

## CI/CD — GitHub Actions + fastlane + TestFlight

Already scaffolded at `.github/workflows/build.yml` and `fastlane/Fastfile` (see `03-CURRENT-STATE.md`
for what's stubbed vs. real). The pipeline:

1. `macos-latest` runner (Apple-hosted, has Xcode preinstalled).
2. Install XcodeGen (`brew install xcodegen`), run `xcodegen generate`.
3. `xcodebuild build` on every push (fast feedback — no signing needed for a plain build/test run).
4. `xcodebuild test` against the `AuraLink` scheme's unit test target.
5. On a tagged release or manual dispatch: `fastlane beta` — builds with App Store Connect API key auth
   (no interactive Apple ID login, works headless in CI), archives, exports a signed IPA, uploads to
   TestFlight.

**What Miel must do manually (cannot be automated by an agent)** — call this out clearly to him, don't
silently block on it:
1. Enroll in the Apple Developer Program (already decided — $99/yr) at developer.apple.com.
2. Create an App Store Connect API key (Users and Access → Integrations → App Store Connect API) and
   add three GitHub Actions repo secrets: `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8` (the key's private
   key file base64-encoded).
3. Register the app's Bundle ID (`com.amielsena.auralink`) in the Apple Developer portal and create the
   App Store Connect app record (App Name "AuraLink", primary language, category, etc.) — this is a
   ten-minute web-console task, not something that benefits from CLI automation given no CLI/API access
   is configured yet in this environment.
4. Add whatever internal/external TestFlight testers he wants (himself first, other Aura 150 owners
   later) via the App Store Connect web UI.

Write the actual GitHub Actions YAML and Fastfile to make steps 1–4 the ONLY manual steps — everything
else (build, sign, archive, upload) must be one click (`workflow_dispatch`) or automatic on tag push.

## Phased build order

1. **Protocol + networking skeleton.** `PxcFrame`, `PxcHandshake`, `EasyConnProber` listening on the
   three ports, QR scan → join flow. Success criterion: connect to the real Aura 150, complete the full
   control-plane handshake (through heartbeats), confirmed via `LogBus` output — **no video yet**.
2. **Video pipeline, minimal source.** `H264Encoder` + `AnnexBConverter` + `FrameQueue`, fed by a static
   test pattern (solid color / test card) instead of MapKit initially — isolates video-path bugs from
   MapKit-rendering bugs. Success criterion: bike shows *something* on screen without disconnecting
   (proves the 9s-timeout / repeat-frame handling works).
3. **Swap in MapKit.** `NavigationCompositor` renders a real map into the pipeline. Success criterion:
   live, panning map on the dash.
4. **Adaptive bitrate + background survival.** Wire `AdaptiveVideoController`, test the phone-locked
   scenario from the "Background execution reality" section above.
5. **UI shell.** Connect/Dash/Setup screens — enough for Miel to operate the app without your direct
   involvement each time.
6. **Remaining features.** Trip logging, handlebar button mapping, Garage multi-bike, Settings, About.
7. **Polish + CI hardening.** TestFlight upload automation, crash-safe logging, review-note prep for
   Apple's background-mode scrutiny.

Do not skip ahead to step 5+ polish before step 1–3 are proven on the real bike — an app with a beautiful
Connect screen that can't complete the PXC handshake is worth less than an ugly one that streams frames.
